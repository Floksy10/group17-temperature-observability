# Что означает Grafana и что ускорено 23 октября

На REST-гистограмме четвёртый столбец `0.05` — это **ответы за 25–50 миллисекунд**. Число **3133 сверху** показывает количество таких ответов. Высокий столбец сам по себе не означает большую задержку: он означает, что много запросов попало в этот интервал.

В конфигурации панели цвет зависит от количества запросов: порог красного — 80. Поэтому столбец с тысячами успешных быстрых ответов может быть красным. Изменять цвет или данные, чтобы скрыть это, мы не стали.

На твоём скриншоте:

- все 182 требуемых уведомления пришли в интервале до 1 секунды;
- пропущенных уведомлений и HashError — 0;
- ошибок обоих REST endpoint — 0;
- около 61% REST-ответов быстрее 50 мс, 83% быстрее 100 мс, 99,5% быстрее 250 мс; все показанные ответы — до 500 мс.

Это разные гистограммы: первая измеряет уведомления, вторая — HTTP-запросы к истории температур.

## Почему мы всё равно продолжили ускорение

Внутри API обработка занимала в среднем примерно 0,9 мс, около 99% запросов укладывались в серверный интервал до 5 мс. Измерение клиента включает дополнительные участки: ожидание обработки входящего запроса, очереди процессов, сеть и получение ответа.

Одинаковые 80 запросов в секунду дали:

| Подача запросов | Среднее | p95 |
| --- | ---: | ---: |
| Равномерно в течение секунды | 2,9 мс | 7 мс |
| Одновременными пачками | 49 мс | 105 мс |

p95 — время, в которое уложились 95% запросов. Пачка создаёт очередь, даже если средняя нагрузка на минутном графике умеренная. Генератор курса тоже работает с пачками.

Групповая VM одновременно держит PostgreSQL, обработку Kafka, уведомления, Docker и Kubernetes control plane. Kubernetes добавляет собственные расходы. Поэтому проверили размещение API на Nick VM, которая уже была включена в кластер.

## Что применено

Теперь Nginx на групповой VM направляет обычные запросы к основному API на **Nick/client4**. На групповой VM остаётся **резервный API**, который используется при недоступности основного.

Минимальное количество API-процессов осталось **два**. HPA может увеличить основной API с одного до трёх, то есть всего максимум четыре API Pod с учётом резерва. Данные PostgreSQL, Kafka topic `experiment` и отправка настоящих уведомлений не изменялись.

Вариант постоянного распределения запросов 4:1 между VM дал нестабильный хвост задержек. Один основной API на Nick справлялся не хуже двух в проверенных сравнениях и требовал меньше памяти. Поэтому выбрана схема основной плюс резерв, а не большее число процессов ради самого количества.

## Результат после применения

Все ответы проверялись на совпадение с сохранёнными реальными историями измерений.

| Проверка | До переноса | После переноса |
| --- | ---: | ---: |
| Пачки по 80 запросов/с, два повторения, p95 | 116–149 мс | **37–48 мс** |
| То же, среднее | 45–47 мс | **19–23 мс** |
| Доля заголовков ответа за ≤50 мс | 66–69% | **96,9–99,7%** |

Дополнительно проверены 250 запросов/с: **5000 правильных ответов, ноль ошибок, p95 60 мс**. Всего после переключения — 7400 правильных ответов без ошибок.

В отдельной тестовой конфигурации основной API был выключен во время непрерывной подачи запросов. Резерв обслужил поток: **7500 ответов корректны**, ошибок нет. Это проверка удаления Pod и перехода на резерв, а не физического выключения VM или отказа PostgreSQL.

Эти результаты относятся к нашему контролируемому тесту публичного API. В финальной проверке источник Grafana вернул пустые RTT-серии group17. Поэтому изменения именно на независимом графике преподавателей ещё предстоит подтвердить свежим потоком курса.

## Что с памятью и CPU

Ось графика памяти увеличена и округляет подписи до 1,72 GiB. Небольшой прирост выглядит как крутой подъём. В первых проверенных 15-минутных окнах разброс был около 19–30 MiB; по этому фрагменту утечку подтвердить нельзя. Долгий тест стабильности отдельно не выполнен.

CPU и память на панели курса относятся к групповой VM. Теперь часть работы выполняет Nick VM. Уменьшение группового показателя само по себе не доказывает экономию всего кластера. Мы не покупали и не увеличивали VM, но снижение общего счёта AWS не измеряли.

Все девять рабочих Pod готовы, рабочая очередь уведомлений пуста. Согласованные 3045 старых тестовых уведомлений остаются сохранёнными, недоставленными и исключёнными из повторов.

## Как посмотреть самому

На групповой VM:

```bash
cd ~/group17-latency-work
sudo k3s kubectl -n temperature get pods -o wide
sudo k3s kubectl -n temperature get hpa,pdb
sudo k3s kubectl -n temperature top pods
python3 scripts/verify_runtime.py
```

У `api` должен быть NODE `nick-client4`, у `api-reserve` — `group17`. Для обычного быстрого пути оставляй Nick VM включённой.

В Grafana выбери `Last 5 minutes`, обнови панель после нового потока преподавателей и сравнивай не высоту красного столбца, а доли ответов за ≤10/25/50 мс, p95, ошибки и достигнутую интенсивность запросов. Все запросы быстрее 5 мс в пачечном профиле пока не продемонстрированы.
