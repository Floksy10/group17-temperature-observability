# Что изменилось и почему система стала быстрее

Главное улучшение — меньше повторной работы при обработке каждого события и запроса. Kubernetes управляет запуском, готовностью и обновлением сервисов; сам по себе он не ускоряет вычисление средней температуры.

## Путь одного измерения

Сенсоры публикуют события в Kafka. Consumer декодирует Avro и объединяет показания сенсоров с одинаковым measurement_id. Когда получены все сенсоры эксперимента, он вычисляет среднюю температуру и сравнивает её с разрешёнными границами. Средняя температура, состояние эксперимента и задание на уведомление сохраняются в PostgreSQL одной транзакцией. Только после успешного сохранения подтверждаются Kafka offsets.

Отдельный notifier забирает задание из outbox и отправляет HTTP-запрос в официальный Notifications API с token. При временной ошибке задание остаётся в БД для повтора. На каждом красном измерении новое уведомление не создаётся: уведомляем при переходе из нормы в состояние вне диапазона. Для этапа стабилизации есть отдельное уведомление.

REST API читает исторические измерения после experiment_started. Два API Pod работают за Nginx. Данные завершённых коротких экспериментов кэшируются; активные измерения читаются из БД, чтобы не возвращать устаревший результат.

## Где выиграли производительность

1. Раньше каждый sensor event требовал отдельной транзакции и нескольких последовательных обращений к БД. Теперь до 64 Kafka-сообщений сохраняются одной транзакцией; ожидание набора ограничено 20 мс. Последовательные показания одного измерения объединяются, а несколько независимых SQL-записей отправляются через pipeline. Это уменьшает число обращений к БД без пропуска сенсоров и смены порядка этапов эксперимента.
2. Запрос короткого временного окна больше не загружает всю длинную активную историю в Python. Фильтрация выполняется индексированным SQL-запросом. В сравнении на истории из 5000 точек p95 снизился примерно с 3,6–4,0 секунды до 94–111 мс.
3. Кэш имеет ограничение по оценке памяти — 32 MiB на worker — и по числу точек. Огромный завершённый эксперимент не занимает кэш целиком.
4. Два consumer оказались быстрее четырёх в проверенном сценарии. Дополнительные процессы конкурировали за CPU и одну БД. Поэтому оставлены два, а не максимальное количество ради количества.
5. API readiness больше не ждёт свободное соединение из того же пула, который используют пользовательские запросы. Иначе при нагрузке Kubernetes мог убрать сразу оба API из обслуживания. Nginx обновляет адреса Pod и повторяет безопасные GET-запросы при смене backend.
6. Notifier объявляется готовым только после подключения к БД. При обновлении старый готовый экземпляр сохраняется, пока новый не сможет работать.

## Что проверено

В окончательном совместном тесте: 100 экспериментов, по четыре сенсора и 20 измерений; параллельно 250 HTTP-запросов в секунду. Все 12 500 HTTP-ответов корректны, ошибок нет. Все 2000 исторических измерений сохранены, незавершённых сенсорных наборов нет. Максимальная задержка тестового уведомления с локальным mock — 0,819 секунды. Это не измерение внешнего сервиса.

Отдельно получены 68 успешных ответов настоящего Notifications API: максимум возвращённой им задержки 0,533 секунды. Нагрузку официального генератора в этой выборке мы не задавали. Во время раннего обновления notifier было одно уведомление на 13,3 секунды; это сохранено в отчёте и стало причиной исправления readiness.

При обновлении API под нагрузкой проверены ещё 3750 ответов: все корректны. Пройдены 30 unit/contract-проверок. Полные результаты и неудачные варианты сохранены в [отчёте](final-performance.md).

## Что произошло со старыми тестами

Старые персональные consumer продолжали читать group17 и писать тестовые события в основную БД через SSH-туннели. Нашлось 3045 недоставленных уведомлений, полностью совпадающих с тестовыми по пяти полям. С твоего разрешения их повторы приостановлены; записи сохранены как недоставленные. Старый сетевой доступ администратора БД закрыт, а новые сервисы работают под отдельными ограниченными пользователями. Локальный административный psql сохранён.

## Что Kubernetes даёт нашей команде

Deployment поддерживает нужное число экземпляров и заменяет упавшие Pod. Readiness определяет, когда экземпляр можно использовать. Service и Nginx направляют HTTP-запросы к готовым API. Requests/limits ограничивают ресурсы. HPA настроен на 2–4 API Pod по загрузке CPU; отдельного успешного срабатывания HPA в тестах пока не демонстрировали.

В кластер фактически включены две VM: групповая и Nick/client4. Ibrahim и Yorick пока не зарегистрированы как Kubernetes nodes: Git-ключ или туннель к БД не означает вступление в кластер. Для них подготовлен [английский runbook](final-kubernetes-runbook.md). Сейчас персональные VM полезно использовать как независимые генераторы нагрузки; размещение приложения на четырёх nodes ещё нужно отдельно проверить.

Уменьшение числа процессов экономит ресурсы приложения, но K3s сам потребляет память. Снижение счёта AWS не доказано: тариф и число включённых VM не менялись. PostgreSQL и control plane остаются на групповой VM, поэтому отказ этой VM пока остановит систему. Это работающая оптимизированная учебная архитектура, а не доказанная промышленная система высокой доступности.

Для ежедневной работы начинай с runbook: SSH → состояние Pod → логи consumer/notifier → проверка API и очереди → Grafana. Перезапускать систему при каждом подключении по SSH не требуется.
